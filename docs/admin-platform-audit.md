# Auditoria — reestruturação do Admin da plataforma

Gerada em 2026-10-31 a partir da leitura (somente leitura) de `hype-backoffice-main` e `hypeapi-repo`. Nenhum banco foi consultado: o que depende do banco real aparece como **UNKNOWN** nos relatórios de apoio (`docs/admin-platform-audit-reports.md`).

## 1. Conclusões

- O projeto **não usa Supabase** (sem RLS, sem Edge Functions no frontend). A autorização é feita nos guards do NestJS (`AuthGuard`, `WorkspaceGuard`, `AbilityGuard`, `PlatformAdminGuard`).
- O frontend do Admin só consome agregados (`/admin/dashboard/*`), comunidade e notificações. Não existe endpoint para listar workspaces, usuários globais, campanhas globais, criadores globais ou movimentações financeiras globais.
- `workspaces` e `users` **não têm status** (ativo/suspenso/arquivado). `workspaces.deleted_at` existe mas nunca é escrito: `DELETE /backoffice/workspaces/:id` é um **DELETE físico em cascata** que apaga saldo (`workspace_balances`), cobranças (`asaas_charges`) e campanhas.
- Criadores são `users.type=10` e cada um ganha um **workspace pessoal** no cadastro; sem filtrar, "total de workspaces" fica inflado por esses workspaces.
- Matriz de viabilidade: **105 itens** — Disponível hoje: 13, Dado existe, falta endpoint: 71, Precisa de migration: 12, Não existe no banco: 9.

## 2. Erros e imprecisões encontrados no que já existe

- IMPRECISE (premise): 'AdminAuditInterceptor -> platform_audit_log' implies admin coverage. It covers only 4 controllers (dashboard, notifications, reports, users-merge); community groups/posts mutations and POST /backoffice/balance/entries (creates withdrawable money) are unaudited, and guard rejections (401/403) and idempotent replays never reach it.
- IMPRECISE (schema comment): lib/db/schema.ts:1712 labels workspace_balances.balance_cents 'Saldo disponivel'; the service semantics are balance = top-ups minus released, available = balance - committed. The comment misled the custody KPI (SUM(balance+committed)).
- IMPRECISE (premise): 'PlatformAdminGuard' guards only the admin module. It also guards 3 balance.controller.ts handlers (influencers/:userId, influencers/:userId/entries, POST entries; :312,:327,:592) and WorkspaceGuard-bypassing routes use isPlatformAdminUser inline.
- IMPRECISE: lib/db/schema.ts types platform_audit_log.user_id as nullable while migration 058:23 declares NOT NULL + ON DELETE SET NULL (self-contradictory); production shape is UNKNOWN.
- IMPRECISE: ClientTypeGuard looks like a boundary but request.clientType is read by nothing; the real boundary is the JWT ability client_type:backoffice, which any user type 20/30/100 receives. users.type=100 is self-registrable via public POST /backoffice/auth/register and grants nothing.
- IMPRECISE: reports state workspaces.deleted_at 'is filtered by dashboards' as if it hid deleted tenants. Since nothing writes it, those filters are no-ops; rows disappear only by hard delete.
- IMPRECISE (frontend): AdminSaasMetrics.ltv_estimate typed number (types.ts:115) but backend may return null; FE AdminNotificationStatus includes draft/partially_failed that the backend never emits.
- IMPRECISE: package.json references db:safe-migrate / db:check scripts that do not exist; only db:migrate (scripts/run-migrations.ts) is real. 'Who deploys' cannot be settled from the repo.
- UNVERIFIED by me at runtime: the claim that createFileRoute(... as ...) casts break the TanStack route generator (frontend report) - static reading only; treat as a build risk to test first, not a fact.

## 4. Contradições entre os relatórios e como foram resolvidas

- Custody: db-financial/backend-admin say SUM(balance+committed) double counts; schema.ts comment and snapshot code imply balance is 'available'. RESOLVED by balance.service.ts:641 and migration 055: committed is a subset of balance, so custody = SUM(balance_cents); committed_cents = of which reserved; free = balance-committed.
- 'Active workspace' has 2-3 definitions: snapshot/churn = non-deleted campaign created OR updated in 30 d; ARPU denominator = campaign updated_at in range; KPI card workspaces_with_active_campaigns = has a published campaign now. RESOLVED: all three exist in code; the rebuild must pick ONE (owner decision) and expose it with its definition string.
- pending_payments: live path = reserved entries created inside the period; snapshot path = cumulative reserved at end of day using CURRENT statuses. RESOLVED: pending is a point-in-time stock, not a period flow; the rebuild should compute SUM(reserved) now and label it 'comprometido'.
- creators_active_30d: snapshot counts any campaign_users.updated_at; live path requires ACTIVE statuses. RESOLVED: use one definition (14 ACTIVE_CU_STATUSES, campaign-capacity SSOT) and drop the snapshot variant.
- Number of audit tables proposed: workspace-lifecycle proposes platform_state_changes, security-migrations proposes platform_admin_action_log. RESOLVED: build ONE append-only table (platform_admin_action_log) written in the same transaction as the state change; do not create both. Keep platform_audit_log as the GET-access trail.
- Pagination: db-campaigns cites PaginationQueryDto/buildPaginationMeta (total_pages 0 when empty) while backend-admin notes admin notifications use total_pages=ceil and reports use max(1,..). RESOLVED: new admin lists should use common/utils/pagination.ts helpers (offset, per_page<=100, meta {page,per_page,total,total_pages}) for tables with page numbers, and the signed cursor helper only for feeds; document the total_pages=0 on empty behaviour.
- Paid definition: 'paid' = released (pending_release|available|withdrawn by released_at) in dashboard vs truly PIX-paid (influencer_withdrawals.status='paid' / asaas_transfers.status='done'). RESOLVED: expose both with distinct labels ('Liberado a criadores' vs 'Pago via PIX'); never call released 'paid'.
- 'Published content' = campaign_contents.status='published' (RPC 025) vs COUNT(identified_posts) (RPC 050). RESOLVED: pick one for 'deliveries' (owner decision); default recommendation = contents.status='published' for deliveries and identified_posts only for reach.
- Mobile 401 vs 403: AuthGuard returns 401 for non-active users, and the mobile app logs out silently on any 401 and treats 403 as permission-only (hypeapp-app-main/utils/session-expiry.ts:1-17). RESOLVED as a design choice, not a code contradiction: login returns explicit 403 + code; in-session suspension uses 401 only if forced logout is desired (owner decision).
- workspaces.updated_at: schema says NOT NULL default now(), but PUT/photo never set it and no trigger exists, so it is not an activity signal. RESOLVED: never use it for 'last activity'.
- Report db-identity says backoffice login has no deleted_at filter; db-campaigns/others imply login rejects deleted users. RESOLVED: backoffice login (auth.controller.ts:62-66) has NO deleted_at filter but every later request is rejected by verifyToken:130, so a deleted backoffice user can obtain a token but not use it; add the filter at login.
