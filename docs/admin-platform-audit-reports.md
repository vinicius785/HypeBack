## 2. Answers

**(1) Platform admin.** `users.platform_role = 'admin'` (schema.ts:77; `src/common/guards/platform-admin.guard.ts:32-38`). Documented values admin|support|finance, but only `admin` is honored; no CHECK. It is NOT `users.type=100`. Assignment: nothing in code, migrations, scripts or docs writes it, so it is manual SQL on the live DB. Read live per request (`src/auth/auth.service.ts:124-157`), so revocation is immediate. Exposed by `GET /backoffice/me` as `is_platform_admin`/`platform_role` (`src/resources/backoffice/user.resource.ts:33-34`). Frontend adds a UI-only e-mail allow-list (`VITE_PLATFORM_ADMIN_EMAILS`). Other role holders: `user_workspace.role`, `users.community_role` (moderator tag, no privileges), `community_group_members.role`. Legacy spatie `roles` (14 rows) and `model_has_roles` (398) appear in the MySQL load report (`db-migration/report_supa_counts.csv:18,31`); no code reads them.

**(2) workspaces.** Owner column: NO. status/active/suspended/archived: NO. `deleted_at`: exists, never written; `DELETE /backoffice/workspaces/:id` is a HARD delete (`src/modules/backoffice/controllers/workspaces.controller.ts:409`). `created_at` yes; `updated_at` exists but PUT/photo never set it (controller 368-380, 447-451). Plan/trial/subscription: NO (absent from schema and src).

**(3) users.** `deleted_at` yes (written only by app self-delete, auth.service.ts:255, and merge, `src/modules/backoffice/services/user-merge.service.ts:175`). status/blocked/suspended: NO (`user_suspended` is only a label on `community_reports.action`). last_login/last_seen: NO. `email_verified_at` yes, but only creator flows set it, never brand users. Phone verified = row in `user_phone_verifications` with phone = `users.phone` (`src/services/phone/phone-verification.service.ts:13-21`). Types (`lib/enums/user-type.ts:1-6`): 10 Influencer, 20 Client (brand), 30 Agency, 100 Admin. Backoffice login accepts 20/30/100 (`src/modules/backoffice/controllers/auth.controller.ts:35-39`); app accepts only 10 (`email-auth.service.ts:28`). Public `POST /backoffice/auth/register` accepts 20/30/100 (`dto/register.dto.ts:12-16`). Creators = `users.type=10`; there is no creators table. Their `social_networks` hang off `workspace_id` (schema.ts:310-339) through a best-effort personal workspace "{First}'s Workspace" (app `auth.controller.ts:259`, `email-auth.service.ts:105`, `apple-auth.controller.ts:199`, `instagram-login.orchestrator.ts:48`; brand pre-registration with `is_external=true`, `campaign-users.controller.ts:1101-1116`).

**(4) Membership.** Only `user_workspace`; many-to-many. Roles (`lib/enums/workspace-role.ts:1-13`): owner, admin, member, aprovador, observador, juridico, financeiro, analista, custom. Non-null `permissions` overrides role defaults for any role (211-223). Owner = `role='owner'`, not a column; several allowed; the "last owner" rule is app-level only (`src/modules/workspaces/workspaces.service.ts:328-386, 420-441`). `admin` has ALL permissions, including `workspace_delete`/`members_role_write` (workspace-role.ts:199-201). Invitations: NO table or status; invite creates the membership immediately: an existing 20/30/100 user is added, an unknown e-mail creates `users(type=20)` plus a 6-digit code in `password_reset_tokens` (1 h) (workspaces.service.ts:150-326). Influencers cannot be invited (213-222).

**(5) Tokens.** `last_used_at` yes: set at creation (auth.service.ts:79), refreshed only when older than 5 min (35-43, 134-155). `expires_at` exists but is never written by current code (73-80; JWT exp 30 d, line 68; legacy Laravel rows UNKNOWN). No revoked column: logout/delete-account DELETE the row (169-186, 212-219); no cleanup job. "Ultimo acesso" = MAX(`last_used_at`) by `tokenable_id` (filter `name='backoffice'`), a lower bound (NULL after logout everywhere).

**(6) On workspace creation** (workspaces.service.ts:60-121): one `workspaces` row plus one `user_workspace` (role owner), as two non-transactional statements. Nothing else; no triggers in repo migrations. `workspace_balances` is upserted on first top-up/commit (`src/modules/balance/balance.service.ts:683,730,775,1207`; absent row = 0); `workspace_contract_defaults` on first contract send (`src/modules/backoffice/services/campaign-contracts.service.ts:570-590`). `lib/actions/create-workspace.ts` is unused legacy.

**(7) Figures**
- Total workspaces: `COUNT(workspaces) WHERE deleted_at IS NULL`; includes creators' personal workspaces. Brand/agency = has a member with `users.type IN (20,30,100)`. Snapshot `platform_metrics_daily.workspaces_total` counts all (`src/modules/admin/services/platform-metrics-snapshot.service.ts:125-128`).
- Active: NOT STORED. Existing definition: at least 1 non-deleted campaign created/updated in 30 d (snapshot:120-124; `admin-dashboard.service.ts:772-773`), column `workspaces_active_30d`.
- Inactive: NOT STORED (total minus active).
- In trial: NOT STORED.
- New in period: `workspaces.created_at` (hard deletes erase history); CTE at admin-dashboard.service.ts:889-893.
- Total users: `COUNT(users) WHERE deleted_at IS NULL` by `type` (includes `is_external` unclaimed stubs and legacy duplicate e-mails).
- Active users: NOT STORED. Proxies: token `last_used_at`; creators `campaign_users.updated_at` 30 d (snapshot:70-72), `user_locations.location_updated_at`.
- Owner + e-mail: `user_workspace.role='owner'` joined to `users.name/email` (0..n owners; pick deterministically).
- Member count: `COUNT(user_workspace)` per `workspace_id`.
- Last activity: NOT STORED at workspace level (`updated_at` unmaintained); derive MAX over `campaigns.updated_at`, `asaas_charges.updated_at`, `workspace_balances.updated_at`, members' token `last_used_at`.

## 4. Top pitfalls
- Hard delete cascades to campaigns, social_networks, asaas_charges, workspace_balances (schema.ts:236,316,1711,1898), orphans `tokens.workspace_id` (1362) and polymorphic integrations; role `admin` can trigger it.
- `deleted_at` is ignored by `WorkspaceGuard` (`src/common/guards/workspace.guard.ts:45-49`); the guard has no platform-admin bypass (57-72). Workspace lists show only the caller's memberships (workspaces.controller.ts:97-115): no cross-tenant list exists.
- `request.user` is the full row including `password`; `integrations.metadata` holds plaintext provider tokens: always use explicit selects or resources.
- An `admin` can promote itself to owner (no actor-role check, workspaces.service.ts:398-471), so "owner" is a soft concept.

### Lacunas

- No cross-tenant workspace list/search/filter/sort/paginate endpoint (only membership-scoped GET /backoffice/workspaces and a top-N ranking); no supporting indexes on workspaces(created_at), workspaces(lower(name)) or trigram
- No cross-tenant user list/detail endpoint (admin has only merge-into); no indexes for admin lookups on users(created_at), users(lower(name)/normalized_email already indexed non-unique) or personal_access_tokens(tokenable_type, tokenable_id, last_used_at)
- No workspace lifecycle state (status/suspended/archived); deleted_at is unused and DELETE is a hard delete; WorkspaceGuard, /me/workspaces and /workspaces ignore deleted_at
- No user suspension/block flag and no enforcement point beyond deleted_at in AuthService.verifyToken; no admin endpoint to soft-delete/restore a backoffice user or revoke all of a user's sessions
- No platform-admin bypass variant of WorkspaceGuard for read-only drill-down into workspace-scoped endpoints (bypass exists only in balance and contract-defaults controllers)
- No plan/trial/subscription/billing model anywhere, so 'em trial' cannot be computed
- No invitation entity (pending/accepted/expired/revoked, inviter, expires_at); invitees are created and added immediately
- No owner designation (owner_user_id), no transfer-ownership endpoint, no DB-level at-least-one-owner protection, no per-actor-role restriction on assigning owner
- No durable last-login/last-seen on users and no workspace-level last_activity; token last_used_at is lost on logout and lags up to 5 min
- No discriminator between brand/agency workspaces and creators' personal workspaces (workspaces.kind) so totals and ratios are inflated unless derived from member types
- Platform roles support/finance are documented but not enforced; no endpoint, UI or documented procedure to assign platform_role or to bootstrap the first admin; no CHECK on platform_role
- No mutation-grade admin audit (actor, target type/id, request body or before/after); platform_audit_log records endpoint and query only and is not applied to community groups/posts controllers
- platform_metrics_daily lacks brand-user totals and brand-vs-creator workspace splits; creators_total includes is_external stubs
- Schema authority gap: base-table DDL not in repo migrations, so CHECKs/indexes on users, workspaces, user_workspace, personal_access_tokens cannot be verified from code
- Referenced specs docs/api-super-admin-dashboard.md and API_BACKOFFICE_WORKSPACES_AND_PERMISSIONS.md are missing from both repos

### Riscos

- Hard delete of a workspace (DELETE /backoffice/workspaces/:id, workspaces.controller.ts:409) cascades to campaigns, social_networks, asaas_charges, workspace_balances, notifications, lives etc. (schema.ts:213,236,316,728,961,1086,1132,1711,1898,2058,2523), has no balance/active-campaign check, orphans tokens.workspace_id and polymorphic integrations (plaintext Page tokens), and is permitted to role admin, not only owner (workspace-role.ts:199)
- workspaces.deleted_at is a semantic trap: dashboards filter on it (admin-dashboard.service.ts:734,891) but WorkspaceGuard (workspace.guard.ts:45-49), /me/workspaces and /workspaces do not, and nothing writes it; any soft-delete or suspend feature must patch all of them
- Non-transactional createWorkspace (workspaces.service.ts:95-118) plus swallowed failures in creator flows (app/auth.controller.ts:258-265 etc.) can leave ownerless workspaces and workspace-less creators; the last-owner rule is check-then-act in service code (race-prone, no DB constraint)
- Admin has every permission (workspace-role.ts:199-201) and updateWorkspaceMemberRole has no actor-role check (workspaces.service.ts:398-471): an admin can promote itself to owner or delete the workspace, so 'owner' in the admin UI must be derived, not trusted
- Counting traps: total workspaces and the daily snapshot include creators' personal workspaces (snapshot service:125-128); total users include is_external unclaimed stubs and legacy duplicate normalized e-mails (non-unique index, user_identity_conflicts); hard deletes erase history so 'new in period' cannot be reconstructed
- Secret/PII exposure: request.user is the full users row incl. password hash (auth.service.ts:124-157); integrations.metadata and Creator Marketplace Page tokens are plaintext; wallets hold encrypted private keys - admin endpoints must use explicit column selects or the existing resources, never select() whole rows
- Platform-admin identification relies on a manually set varchar with no CHECK; only 'admin' works; users.type=100 is self-registrable via public POST /backoffice/auth/register (register.dto.ts:12-16) and must never be used for authorization; frontend VITE_PLATFORM_ADMIN_EMAILS and the 'platform:admin' ability check are client-side only and should be removed
- Reset/invite codes: 6-digit code is the lookup key stored in password_reset_tokens.token with a global UNIQUE index (schema.ts:147) and reset-password has no e-mail binding (auth.controller.ts:284-292); invite uses Math.random and writes membership and code in parallel (workspaces.service.ts:297-315) so a collision leaves user+membership without code and a retry returns 409; no cleanup job; only the global 100/60s throttle protects brute force
- Token table semantics: no revoked column, expires_at never written, rows accumulate with no cleanup, last_used_at lags up to 5 min and disappears on logout, DB abilities column is never read (AbilityGuard uses the JWT); last-access queries need an index that is not declared (live index state UNKNOWN)
- Schema drift: base tables absent from migrations; user_workspace.permissions json (Drizzle, migration 075) vs jsonb (migration 030); workspace_balances/platform_audit_log are timestamptz in SQL but timestamp in Drizzle; platform_audit_log.user_id NOT NULL with ON DELETE SET NULL in 058 vs nullable in Drizzle; package.json lists nonexistent db scripts and drizzle-kit push exists - verify live DDL before relying on any constraint
- RLS/Data API exposure of core identity tables is UNKNOWN: only migrations 093/095 enable RLS and revoke anon/authenticated; users (password hashes) and personal_access_tokens may be reachable through Supabase's Data API if it is enabled - verify relrowsecurity and grants
- Legacy spatie tables roles (14) and model_has_roles (398) appear in the MySQL load report but are unread by code; contents/presence UNKNOWN and they must not be treated as an authority for admin roles
- Audit gaps: AdminAuditInterceptor is fire-and-forget, records endpoint+query only, and is absent from community groups/posts admin controllers; new destructive admin operations (suspend, delete, role change, session revoke) need body/target capture and non-lossy logging
- Dead legacy code that is unsafe if reused: lib/auth/sanctum.ts (default JWT secret fallback, unthrottled last_used write) and lib/actions/create-workspace.ts (no dedupe, CNPJ check or transaction)
- Backoffice login/register compare raw users.email (auth.controller.ts:65,130) while the trigger lowercases and guards on normalized_email (078:52-69): mixed-case input can miss existing accounts and surface as a generic 500 (23505) on register
- StoreWorkspaceDto caps name at 20 chars but the column and update DTO allow 100 (store-workspace.dto.ts:16 vs update-workspace.dto.ts:15), and workspace tax_id is not unique, so admin dedupe/search by CNPJ may return several workspaces

## db-financial

**Bottom line.** BRL money is integer cents in two mutable state-machine ledgers (`asaas_charges` in; `influencer_balance_entries` + `influencer_withdrawals` out) plus a balance cache (`workspace_balances`). There is no fee model, no invoices, no payable due dates, and `users_payments` is never written. KPI SQL exists but has defects (see 3 and Top risks).

**1. Units / currency**
- BRL integer cents (INT4): entries `amount_cents` (schema.ts:1582), withdrawals (:1631), `workspace_balances.balance_cents/committed_cents` (:1713/1715), `asaas_charges`/`asaas_transfers` (:1901/1943). No currency column (BRL implied); INT4 caps a balance at R$ 21.474.836,47.
- Dashboard API returns BRL as JS float via `centsToBrl` (admin-dashboard.service.ts:536-539); snapshot columns are BIGINT cents (059_platform_metrics_daily.sql:48-52).
- HYPE on-chain is a separate unit: wei `varchar(80)` (schema.ts:1394, 1469, 1513), never converted to BRL. `users.hype_points` (:105) is not money.
- Legacy reais floats: `payment_method_details.amount|value` (balance.service.ts:89-92), CPM rate (cpm-rate.ts:9-15). Current fixed prices are cents in step contents (lib/utils/campaign-fixed-price.ts:2-6).

**2. Ledger model (source of truth as implemented)**
- Aportado por clientes / volume movimentado: `asaas_charges` with `paid_at` (volume = deposits, a proxy).
- Saldo em custódia: `workspace_balances` (formula defective).
- Pago aos criadores: entries `pending_release|available|withdrawn` by `released_at`, meaning *released*, not PIX-paid.
- Pagamentos pendentes: entries `reserved`. Receita de taxas: none (hard-coded 0).
- Entry status (varchar, app-level only, 065:20-22): `reserved` (locked for active campaign), `cancelled`, `pending_release` (30-day hold), `available` (cron 02:00), `withdrawn` (set at withdrawal *request*, reverts on failure, balance.service.ts:543-584). Withdrawal: `pending|paid|failed`. Charge: `pending|received|cancelled` (Asaas OVERDUE/CANCELLED become `cancelled`, asaas.service.ts:299-304). Transfer: `pending|bank_processing|done|cancelled|failed`.
- Mechanics: top-up `balance+=`; reserve `committed+=`; release `balance-=` and `committed-=` (balance.service.ts:858-867); CPM payout `balance-=` only (cpm-payout.service.ts:249-255); `available = balance - committed` (balance.service.ts:641). So committed is a subset of balance. Identity (no manual credits/orphans): Σreceived charges - Σpaid withdrawals = Σbalance_cents + Σ(pending_release+available) + in-flight withdrawals.
- Not append-only: reserved amounts mutate (:1241-1245), withdrawals split entries (:388-415).

**3. Existing KPI definitions** (admin-dashboard.service.ts; fallback :565-628, snapshot :543-563)
- custody (:576): `COALESCE(SUM(balanceCents + committedCents),0)::bigint` double-counts committed (schema.ts:1712 mislabels balance as "disponível"); snapshot :102-104.
- deposits/volume (:585-590, :623): `paid_at IS NOT NULL AND paid_at BETWEEN from AND to`.
- paid (:599-605): `status IN (pending_release,available,withdrawn) AND released_at IS NOT NULL AND released_at BETWEEN`.
- pending (:616-617): `status='reserved' AND created_at BETWEEN` (period-limited); snapshot is cumulative `status='reserved' AND created_at<=endOfDay` (platform-metrics-snapshot.service.ts:114-117).
- fees: `0` (:626; snapshot :118).
- `volume_series` (:637-675): deposits by `paid_at`, payments by `released_at`; the chart sums both (admin-financial-volume-chart.tsx:105-111), the KPI card shows deposits only.
- Periods are UTC (:91-97). Snapshot is read only for the exact `to` date (:178-185) and the job writes yesterday (snapshot.service.ts:47-49), so presets ending today use the fallback.
- ARPU/NRR/LTV use deposits as revenue proxy (:810-869); ranking volume = deposits (:707-713).

**4. Movements and links**
Per workspace: yes, `GET /backoffice/balance/workspace/:uuid/movements` (financial-reports.service.ts:131-490; platform admins pass `resolveWorkspace`, balance.controller.ts:201-218). It merges charges and entries joined to campaigns into 7 virtual types (:73-82). Global: **no**. `hold_id` is always null, `user_id`/`withdrawal_id` are not returned, INNER JOIN drops entries with NULL `campaign_id` (:223-226), SQL has no `to`/limit (:232-240).
Link columns: entries `user_id`, `campaign_id`, `campaign_user_id`, `social_network_id`, `withdrawal_id`, `public_id`; no `workspace_id` (derive via `campaigns.workspace_id`), actor, charge, contract or post id. `asaas_charges.workspace_id/asaas_id/public_id`; `asaas_transfers.withdrawal_id` leads to `influencer_withdrawals.user_id`. **Top risks**
1. Custody KPI double-counts `committed_cents`.
2. Workspace/campaign hard delete wipes `workspace_balances`, `asaas_charges`, holds and orphans `reserved` entries (committed never refunded).

7. Schema drift: SQL-only indexes/FK vs schema.ts, and `asaas_*` DDL not in any migration.

## 3. Dashboard metrics (`admin-dashboard.service.ts`)
- Period: `from` becomes 00:00Z, `to` 23:59:59.999Z, default to=now, from=to-30 d (`:91-97`); UTC only; no from<=to or max-range check; `IsDateString` is an ISO-8601 alias, so a timestamp yields `Invalid Date` and 500. Granularity maps to `date_trunc(day|week|month)`; labels `YYYY-MM-DD`/`YYYY-MM`; empty buckets omitted.
- Two paths per KPI: snapshot (`platform_metrics_daily` row for `to`) or live. The default UI (`to`=today) effectively never has a row, so it runs live. Drift: creators `active_in_period` is any `campaign_users` update in 30 d (snapshot) vs ACTIVE statuses in range (live); `pending_payments` is cumulative reserved (snapshot) vs reserved created in range (live); live hard-codes `total_social_networks=0` and `avg_networks_per_creator=0`; with a missing snapshot day, `new_in_period`/`created_in_period` silently become ONE day's value (`:236-237,428-429`).
- Creators: total = `users.type=10` and `deleted_at IS NULL`; new = same by `created_at`; `activation_rate` = active/total x100. ACTIVE = 14 statuses (approved..completed; excludes applications, curation, pre_selection*, invited, rejected, price_*, contract_pending). Niche/size distributions ignore the period; niche % is a share of memberships (primary+secondary); size buckets from `users.max_followers` (<1k ugc, <10k nano, <100k micro, <500k mid, <1M macro, else mega; zero followers land in ugc).
- Campaigns: non-deleted counts by status (only draft|published|finished); `avg_influencers_per_campaign` = all-time ACTIVE campaign_users / campaigns; `workspaces_with_active_campaigns` = distinct workspaces with a published campaign now; `draft_to_active_rate` = share of created-in-period not draft; evolution published/finished = current status with `updated_at` in range (no history table).
- Financial: custody = sum(balance+committed) over all `workspace_balances`; deposits = sum `asaas_charges.amount_cents` with `paid_at` in range; `paid_to_creators` = entries released in range with status pending_release|available|withdrawn (released, not cash out); `platform_fees` = 0.
- Ranking: all non-deleted workspaces; `active_campaigns` (published, all-time), `total_volume` (paid charges in range), `influencers_contracted` (distinct ACTIVE creators, all-time, includes deleted campaigns); ORDER BY metric, no tiebreak.
- SaaS: "active workspace" has three definitions: churn = non-deleted campaign created OR updated in a 30-day window; ARPU denominator = campaign `updated_at` in range; KPI card = has a published campaign. Churn = (A-B)/A, A active in [from-30 d, from], B = of A also active in [to-30 d, to]. ARPU = paid volume / active workspaces (no fees). LTV = ARPU/churn (null at 0). NRR = volume(to-30 d..to) / volume(from-30 d..from). Client activation = share of workspaces created in range with a campaign created within 30 d (drafts count); creator activation is the separate `activation_rate`. Lifetime = avg(max updated - min created), period-independent. `cac` null.
- Cache: in-process Map, 60 s (creators/niche/size/campaigns/saas/ranking); summary and financial uncached.

### Riscos

- Security/integrity: any workspace Admin or Owner can hard-delete the tenant today (workspaces.controller.ts:402-415) and Member/Analista/Admin/Owner can hard-delete campaigns (campaigns.controller.ts:1919-1959); a new soft state is meaningless until these are neutralised.
- Money: hard delete cascades workspace_balances (unspent brand credit and committed_cents), asaas_charges (including pending PIX) and influencer_balance_holds, while entries/users_payments survive unlinked (SET NULL); reserved entries become permanently stuck and the invariant balance = top-ups - released, committed = SUM(reserved) can no longer be recomputed.
- Money: pending Asaas PIX charges stay payable at Asaas (due +1 day) and no cancel API wrapper exists; the poller credits any pending row, so cascade-deleted rows turn late payments into unreconciled cash.
- Money: withdrawals are paid automatically at request time; asaas_transfers in pending/bank_processing cannot be stopped by code, and user hard delete would cascade influencer_withdrawals -> asaas_transfers, losing reconciliation of in-flight PIX.
- Money: self-delete (me.controller.ts:284-299) anonymises accounts holding available/pending_release entries, pending withdrawals or holds; wallets with encrypted private keys, user_workspace and social_networks remain.
- Creators' data loss: workspace/campaign delete removes their content, scripts, chat history, evaluations (reputation) and notifications; shipments in transit lose their records.
- Privacy: campaign-linked private community groups become public/self-joinable when the campaign_community_groups row cascades away (groups.controller.ts:77-91).
- Legal: signed contract rows (campaign_contracts, signed_file_url) cascade; the signed originals stay at n8n/DocuSign; later callbacks are dropped; workspace_contract_defaults and automation_influencers hold CNPJ/CPF/bank/PIX PII.
- Dangling secrets: integrations rows (SocialNetwork OAuth tokens) and tokens.workspace_id have no FK and survive; refreshAllUsers keeps calling providers for every social_networks row, including those of deleted/suspended owners.
- Storage orphans: Spaces keys campaigns/{public_id}/..., community-lives/..., legacy Supabase bucket and local /uploads/* volume are never cleaned; only single-object deleteFile exists.
- Enforcement gaps: sockets authenticate only at handshake and survive suspension (single process, no adapter); the public invite cache serves a suspended campaign for up to 5 minutes; ~25 mobile queries, brand catalogs, public pre-register and automation M2M ignore state.
- Mixed domain: every creator owns a personal workspace holding their social_networks (UNIQUE workspace_id,type); suspending/deleting such a workspace is really a user operation, and the app resolves it by unordered limit(1).
- Auth UX: AuthGuard returns 401 for non-active users, which the mobile app treats as session expiry (silent logout); login must return an explicit 403 code, and backoffice login (auth.controller.ts:62-66) has no deleted_at filter at all.
- Audit: platform_audit_log is fire-and-forget with no reason/target/body and a contradictory NOT NULL + SET NULL FK (058:23); destructive actions need a transactional append-only record written in the same transaction as the state change.
- Schema drift: four workspace-adjacent tables lack DDL in the repo, a pg_notify trigger is undefined in repo, and drizzle-kit push is available; cascade conclusions are valid only for repo-visible DDL.
- Data model: workspace_balances is a mutable counter (int4 cents) with no ledger; suspension/deletion must snapshot balances, entries by status and charges before changing state.
- Hard-deleting users is unsafe: CASCADE wipes ledger/wallets/withdrawals/campaign participation; NO ACTION/RESTRICT (niche_user, tokens.creator_user_id, platform_notifications.created_by_user_id, token_operations.wallet_id) also makes it fail unpredictably.
- Time-based jobs continue after suspension unless gated: finalization 01:00, release 02:00, CPM 03:00, calendar/publication 09:00, holds hourly, e-mail journey 5 min, notification dispatch 30 s; Asaas credit/transfer polling must NOT be gated or money is left unrecorded.
- Existing bug that suspension would inherit: brand catalogs list soft-deleted (anonymised) creators because influencers-catalog.controller.ts:525,882 do not filter deleted_at.

### Riscos

- `POST /backoffice/auth/register` is public, allows `type=100` and yields a backoffice token instantly (no e-mail verification), and sends a welcome e-mail per call: anyone can hold a backoffice token, so every backoffice route must be Workspace- or PlatformAdmin-guarded. Never authorize on `users.type === 100`; it grants nothing today (grep) but is self-assignable.
- Backoffice reset-password accepts a 6-digit code without e-mail, looks it up globally, has no attempt counter and only the 100/min/IP/handler limit, and does not revoke sessions: a known admin e-mail can be targeted by triggering forgot-password and guessing codes within 1h from many IPs (not exploited or tested here).
- 23 of 29 `@Throttle` decorators are inert (unregistered names); admin routes get only the global 100/60s per IP per handler, counted before authentication; behind NAT admins share a bucket. `TRUST_PROXY` may be unset in prod (then all users share one bucket per handler) and `docker-compose.yml:38-39` publishes port 3000 on all interfaces (if reachable directly together with `TRUST_PROXY=1`, `X-Forwarded-For` can be spoofed to dodge limits and forge audit IPs). Production env is UNKNOWN.
- The frontend logs the user out on 429 (`src/screens/(private)/_layout.tsx:36-37`), so tightening throttles on `GET /me` can sign admins out.
- Admin token is a 30-day JWT in `localStorage` on an origin shared with the marketing site (XSS-exposed, no rotation, no revoke-all); `VITE_PLATFORM_ADMIN_EMAILS` ships admin e-mail addresses in the public bundle (do not print or log the value).
- Audit gaps: `POST /backoffice/balance/entries` (money creation), community group/post deletes and moderator changes are unaudited; guard rejections are unrecorded; rows are fire-and-forget; `query` can store PII search terms; table is mutable; migration 058 (`user_id NOT NULL` + `ON DELETE SET NULL`, BIGSERIAL, timestamptz) vs `schema.ts:2264-2276` mismatch makes the production shape UNKNOWN (check `\d platform_audit_log`).
- `verifyToken` does not bind `personal_access_tokens.tokenable_id` to the JWT `userId` (`auth.service.ts:106-122`) and trusts JWT abilities; the `token` column index is not defined anywhere in the repo (UNKNOWN, check `\d personal_access_tokens`); the table is never purged (6154 rows in `db-migration/report_supa_counts.csv:25`).
- Hard-coded fallback secrets: `auth.service.ts:26`, `unsubscribe.service.ts:34-38` (no production guard, `UNSUBSCRIBE_SECRET` undocumented), `cursor-pagination.ts:29`, `lib/utils/social-verification-token.ts:84`, `lib/auth/sanctum.ts:8` (dead code); `NODE_ENV` must be exactly `production` (set in `Dockerfile` and `docker-compose.yml:41`).
- `request.user` is the full `users` row including the password hash; never return `@User()` directly, use `transformBackofficeUser`.
- Migration process: the production applier is UNKNOWN and docs conflict; `schema_migrations` baseline status is UNKNOWN; a blind `pnpm db:migrate` would also apply any pending data migrations (088/090/091 update specific users by hard-coded identity), so always run `--dry-run` first; editing an applied file breaks the runner; numeric prefixes are not unique (015/016/048/049); old files with explicit `BEGIN/COMMIT` (e.g. 078) conflict with the runner's own transaction, so do not copy them; `db:push`/`db:generate` must not touch prod because `schema.ts` does not model functions, triggers or RLS.
- RLS plus `REVOKE ... FROM anon, authenticated` exists only in 093/095; the API connects with the `DATABASE_URL` role (unknown, possibly bypassing RLS) and whether the Supabase Data API is enabled is UNKNOWN, so every new table must copy RLS + REVOKE.
- `@Body()` with inline types or `any` bypasses `whitelist`/`forbidNonWhitelisted`; `enableImplicitConversion` can turn the string `'false'` into `true` for boolean DTO fields (`me.controller.ts:88` works around it by comparing strings); admin DTOs need classes and explicit `@Transform`.
- Three different 'admin' concepts (`users.type=100`, `user_workspaces.role='admin'`, `users.platform_role='admin'`); `WorkspaceGuard` has no platform-admin bypass and prefers `:id` over the `workspace-id` header (`workspace.guard.ts:29`), so admin features need separate `/backoffice/admin/*` routes without WorkspaceGuard.
- Idempotency cache falls back to memory without Redis (`redis-cache.service.ts:50`); destructive admin actions need a DB-level idempotency key.
- Global 25 MB JSON/urlencoded limit applies to every route, including public ones, on a 1 GB droplet (`main.ts:62-65,81-84`).
- `test/*.e2e-spec.ts` use `DATABASE_URL` from `.env` (rollback only): never run them with production credentials. The installed `node_modules` is a symlink outside the repo and differs from `pnpm-lock.yaml` (throttler 6.7.1 vs 6.5.0, express 5.3.0 vs 5.2.1), so verify throttler behavior against the locked version.
